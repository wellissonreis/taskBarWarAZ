# T2.4 — AtomicFileWriter + SettingsStore

Data: 2026-11-10. Worker claude2. Referências: PLANO T2.4, SDD-14 RF-14.2, RF-14.3, RF-14.4, RF-14.9, CA-14.2/CA-14.3 (Settings), ADR-031.

## O que foi feito
- `IO/IFileSystem` (porta fina), `IO/RealFileSystem`, `IO/AtomicFileWriter` (.tmp com WriteThrough+flush, Replace→.bak ou Move; fallback Copy+Move em IOException/PlatformNotSupportedException; 2 retentativas de 50 ms em IOException; depois log de erro e `false`, nunca lança; UnauthorizedAccess → `false` sem retry).
- `JsonEnvelope` (schema, schemaVersion, appVersion, savedAtUtc, contentHash = SHA-256 hex do payload re-serializado compacto; leitura valida ≤1 MB, JSON, schema, versão futura, payload e hash).
- `IO/CorruptQuarantine`: move para `corrupt\<nome>-<yyyyMMddHHmmss>.json` (sufixo `-N` em colisão), poda para 10 (mais antigos pelo carimbo do nome).
- `Settings/AppSettings` (modelo ADR-031), `SettingsSerializer` (manual, sem reflexão; validação por campo → padrão do campo), `SettingsStore` (Load: principal → quarentena → .bak → padrões; Save atômico).
- Testes: `tests/SideWar.Persistence.Tests` (FakeFileSystem com injeção de falhas; AtomicFileWriterTests, SettingsStoreTests): 35 testes.

## Comandos e resultados
```text
scripts/wsl/build.sh Release -> 0 Warning(s), 0 Error(s)
scripts/wsl/test.sh          -> Core 2, Runtime 74, Persistence 35, todos passando
git diff --check             -> sem saída
```

## Medido
Escrita nova (Move) e existente (Replace+.bak); fallback Copy+Move; retentativas (2×50 ms) e falha final com log e `false`; original intacto em falha; round-trip real no disco (WSL); settings: padrões, round-trip de todos os campos, campos removidos ausentes, T-14.2 (campo inválido→padrão, demais mantidos), fps só 20/30/60 e 4/8, T-14.3 (truncado, JSON inválido, versão futura, hash divergente, schema errado, >1 MB, sem payload → `corrupt\` + .bak ou padrões), poda a 10, colisão no mesmo segundo, erro de leitura → padrões.

## NÃO medido
- CA-14.2 (Stop-Process -Force ×200 em Windows, T-14.3): exige harness com processo filho em Windows; só a lógica com FS falso e o disco real do WSL foram testados.
- `File.Replace` real em NTFS e o fallback em volume sem suporte; antivírus real.
- Migrações (RF-14.10), pasta de dados/modo portátil (RF-14.1), debounce de 500 ms e HUD "falha ao salvar" (fora da ficha).

## Decisões e limitações
- Modelo de Settings fica em `SideWar.Persistence/Settings` (Core não tem modelo; escopo permitido).
- `autoScale` é campo de topo do payload (ADR-031 o lista como editável; RF-14.4 o chamava de estado do jogo — conflito entre texto ajustado e ADR; seguiu-se o ADR-031).
- Mantidos `dock.monitorDevice/boundsHint/reserveSpace`, `opacity.peek`, `behavior.autoPassiveSeconds/peekOnHover`, `performance.saverOnBattery/forceSaver`, `audio`, `diagnostics`, `taskbar.useUia`, pois o RF-14.4 não os removeu. `logLevel` ∈ Debug/Info/Warning/Error (valores não especificados na SDD).
- `contentHash` do envelope é verificado em settings: edição manual que altere valores sem recalcular o hash vai para `corrupt\` (CA-14.3 lista hash divergente). Espaços em branco não afetam o hash.
- Atalhos validados só por formato ("Mod+Tecla", 2–5 tokens alfanuméricos); conflitos/resolução real são da plataforma. Valores de enum (`hideOnFullscreen`) conforme SDD-06.
- schemaVersion < 1 é tratado como corrompido (sem migrações na v1).
- Sem debounce no store; fica para quem o chamar (App).
