## Decisões e limitações
- `TreeScope_Parent` **não é aceito** pelo `IUIAutomationCacheRequest` (ArgumentException no setter, verificado no Windows). O cache usa `Element|Children` e `ParentClassName` é derivado dos filhos em cache (chave classe+AutomationId+retângulo). Condição da busca: `TrueCondition` + filtro por ControlType no código (evita VARIANT em `CreatePropertyCondition`); desvio mínimo de RF-21.3.2/3.
- `HasNotificationAreaAncestor`: botão contido num Pane/Group cuja classe começa com `SystemTray.`; no build testado os botões `SystemTray.*` já são pegos por C2 pelo prefixo (o Pane da bandeja é `TrayNotifyWnd`, sem prefixo), então a regra de ancestral é só reforço.
- Após a 3ª falha não há retry automático (o spec só prevê retry em 5 s para 1–2 falhas); novo gatilho/`Show`/`TaskbarCreated` volta a consultar.
- Consulta imediata (`SetVisible(true)`) e retry usam o mesmo caminho `RunQuery`; um pedido que chega com consulta em voo vira "pendente" (no máximo um) e sai quando ela retorna.
- Privacidade: `AutomationId` dos botões de app contém identificadores de aplicativos (ex.: `Appid: <app>`). O spec manda gravar `AutomationId`, então o dump os contém; **revisar o JSON antes de commitar fixtures** (RF-21.9 / risco "fixtures com dados pessoais"). Nome do elemento nunca é lido.
- Dependência para a integração: o host deve chamar `TaskbarService.OnWake` a cada wake (o callback `wake` do construtor serve para acordar a T-Game vindo da thread Shell), `SetVisible` em Show/Hide, `Signal` nos gatilhos, `TaskbarTriggers.Classify` no WndProc, `TaskbarWatcher.Install/Uninstall` em Show/Hide e `ExplorerRestarted`.
